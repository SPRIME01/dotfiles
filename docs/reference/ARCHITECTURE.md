## 1. High-Level Architecture

### Host Roles

| Host | Role | Shell |
|------|------|-------|
| **Windows** | Bootstrap anchor, terminal host | `pwsh` (PowerShell 7) |
| **WSL (Ubuntu)** | Primary dev environment | `zsh` / `bash` / `pwsh` |

Windows is the **outer shell**: it owns `$PROFILE`, starts the terminal session, and performs Windows-only setup (Terminal-Icons, `PSModulePath` scrubbing). It then reaches into WSL over UNC to load the actual developer configuration that lives in the repo.

WSL is the **inner environment**: all code editing, git operations, and POSIX tooling happens here. The repo stays in WSL at `/home/sprime01/dotfiles` and is never symlinked into Windows.

---

### Windows → WSL Profile Bridge

When a Windows `pwsh` session starts, it reads:

```
Microsoft.PowerShell_profile.ps1
```

This file is the **Windows bootstrap profile** (generated by `just setup-pwsh7`). It:

1. Resolves the repo path over UNC: `\\wsl.localhost\Ubuntu\home\sprime01\dotfiles` (falls back to `\\wsl$\Ubuntu\...`)
2. Sets `DOTFILES_ROOT` and `PROJECTS_ROOT`
3. Strips OneDrive entries from `PSModulePath`
4. Imports **Terminal-Icons** (Windows-only)
5. Uses recursion-safe guard variables (`DOTFILES_WINDOWS_BOOTSTRAP_LOADING`, `DOTFILES_WINDOWS_BOOTSTRAP_LOADED`)
6. Dot-sources the WSL-side repo profile via UNC

```powershell
$mainProfile = Join-Path $env:DOTFILES_ROOT 'PowerShell\Microsoft.PowerShell_profile.ps1'
. $mainProfile
```

> **Key principle:** The Windows bootstrap profile is short and disposable — it is regenerated by `just setup-pwsh7`. All real developer configuration lives in the repo.

---

### WSL-Side Repo Profile

The repo profile lives at:

```
PowerShell/Microsoft.PowerShell_profile.ps1
```

It handles:
- Setting `DOTFILES_ROOT` / `PROJECTS_ROOT` / `USERPROFILE` portably
- Dot-sourcing `shell/integration.ps1` (the modular bridge)
- Loading `.env` files via `PowerShell/Utils/Load-Env.ps1`
- Initialising `oh-my-posh` with an application-only command lookup
- Importing `PSReadLine` and configuring it only when console output is interactive
- Dot-sourcing `.shell_theme_common.ps1`
- Configuring `PNPM_HOME`
- Declaring **lazy-load proxy functions** for `Aliases.psm1`
- Applying recursion-safe guard variables (`DOTFILES_PWSH_PROFILE_LOADING`, `DOTFILES_PWSH_PROFILE_LOADED`)

---

### How the Modular Loader Works

```
shell/integration.ps1   ← dot-sourced by repo profile
        │
        └──► shell/loader.ps1   ← executes the five-step load sequence
                    │
                    ├── shell/common/environment.ps1
                    ├── shell/common/aliases.ps1
                    ├── shell/common/functions.ps1
                    ├── shell/platform-specific/<windows|linux|macos>.ps1
                    └── shell/powershell/config.ps1
```

`integration.ps1` is a thin guard: it resolves `DOTFILES_ROOT`, checks that `shell/loader.ps1` exists, and invokes it. It sets `MODULAR_POWERSHELL_LOADED=true` when done and uses `DOTFILES_MODULAR_PWSH_LOADING` to prevent re-entrant loops. Set `DOTFILES_PWSH_DEBUG=1` in your environment to get verbose trace output.

`loader.ps1` calls each configuration file by dot-sourcing it into the calling scope so all functions and variables survive. It detects the platform via `$IsWindows` / `$IsLinux` / `$IsMacOS` and loads the matching `platform-specific` script.

The **bash/zsh counterpart** is loader.sh, which performs the same five steps for POSIX shells and is sourced from `.bashrc` / `.zshrc` via `.shell_common.sh` (or `.shell_init.sh` in the simplified zsh path). In zsh, loader root resolution uses `${(%):-%x}` to resolve sourced script location correctly.

## 2. PowerShell Loading Pipeline

### Execution Order (Windows session)

```
1. Windows bootstrap profile         (C:\…OneDrive\…\Microsoft.PowerShell_profile.ps1)
2.   ├─ Re-entry guard (`DOTFILES_WINDOWS_BOOTSTRAP_LOADING`)
3.   ├─ Strip OneDrive from PSModulePath
4.   ├─ Import Terminal-Icons (Windows-only, guarded by $IsWindows and ListAvailable)
5.   └─ dot-source repo profile      (\\wsl.localhost\…\PowerShell\Microsoft.PowerShell_profile.ps1)
6.         ├─ Profile guard (`DOTFILES_PWSH_PROFILE_LOADING`)
7.         ├─ Set env vars (DOTFILES_ROOT, PROJECTS_ROOT, USERPROFILE)
8.         ├─ dot-source shell/integration.ps1
9.         │       └─ invokes shell/loader.ps1 →
10.        │               ├─ shell/common/environment.ps1
11.        │               ├─ shell/common/aliases.ps1
12.        │               ├─ shell/common/functions.ps1
13.        │               ├─ shell/platform-specific/windows.ps1  (on Windows)
14.        │               └─ shell/powershell/config.ps1
15.        ├─ Load .env files via PowerShell/Utils/Load-Env.ps1
16.        ├─ Init oh-my-posh (application command only)
17.        ├─ Import PSReadLine + configure (interactive-safe)
18.        ├─ dot-source .shell_theme_common.ps1
19.        ├─ Set PNPM_HOME
20.        └─ Register lazy-load proxy functions for Aliases.psm1
```

---

### File-by-File Breakdown

| File | Responsibility |
|------|----------------|
| `Windows bootstrap profile` | Regenerated by setup-pwsh7.sh. Short-lived glue. Sets roots, strips OneDrive from `PSModulePath`, imports Windows-only modules, dot-sources repo profile. |
| Microsoft.PowerShell_profile.ps1 | Main developer profile. Lives in repo. Idempotent. Safe to run on both Windows and WSL `pwsh`. Includes re-entry guard and command-availability hardening. |
| integration.ps1 | Guard + dispatcher. Resolves `DOTFILES_ROOT` as a fallback and delegates to loader.ps1. Includes `DOTFILES_MODULAR_PWSH_LOADING` loop guard. |
| loader.ps1 | Five-step ordered loader. Each step is guarded with `Test-Path` so missing files produce a warning, not a crash. |
| environment.ps1 | Path additions (`~/.local/bin`, cargo, go, etc.), editor defaults, `NODE_ENV`, UTF-8 encoding. Also dot-sources any `*.ps1` in ps1. |
| aliases.ps1 | Short navigation aliases (`ll`, `..`, `gs`, `gp`, etc.) and generic dev aliases. All cross-platform. |
| functions.ps1 | Reusable utility functions: `mkcd`, `ff`, `fd`, `Get-PublicIP`, etc. |
| windows.ps1 | Windows-only: winget/choco/scoop wrappers, `sudo`, `explorer.`, etc. Wrapper creation is gated by application-command checks. |
| linux.ps1 | Linux/WSL-only: `apt` wrappers and equivalent helpers (if present). |
| config.ps1 | PowerShell runtime tuning: `PSDefaultParameterValues`, PSReadLine key bindings, `$MaximumHistoryCount`, `which` alias via `Get-CommandSource`. |
| .shell_theme_common.ps1 | PSReadLine configuration (interactive-safe), VS Code shell-integration injection (application-command lookup, idempotent guard, UNC/WSL-network path skip). |
| Load-Env.ps1 | Reads .env files (key=value format) into `$env:*` variables. Called for repo root .env and `mcp/.env`. |
| Aliases.psm1 | Heavy module with all complex functions (git, file, network, system, etc.). **Never imported at startup.** Only loaded on first invocation of a proxy function. |

---

### Lazy-Loading of Aliases.psm1

Every exported function in `Aliases.psm1` has a thin proxy defined at the bottom of the repo profile:

```powershell
function finddir { Import-Module $aliasesModulePath -Force; Find-Directory @args }
function gs      { Import-Module $aliasesModulePath -Force; Get-GitStatus @args }
# … and so on
```

The first call to any of these imports the entire module (idempotent thanks to `-Force`). This keeps startup time fast: `Aliases.psm1` is only pulled in when you actually use a function from it.

> **When you add a function to `Aliases.psm1`**, you must also add a proxy at the bottom of the repo profile. Use `updatealiases` (itself a proxy) to regenerate all proxies automatically.

## 3. Module-Loading Rules

### Module Ownership Table

| Module | Windows | WSL pwsh | Notes |
|--------|---------|----------|-------|
| `Terminal-Icons` | ✅ | ❌ | Loaded in Windows bootstrap only. Uses `$IsWindows -and PSEdition -eq 'Core'` guard. |
| `PSReadLine` | ✅ | ✅ | Loaded in repo profile + config.ps1. Idempotent check: `if -not (Get-Module ...)`. |
| `oh-my-posh` | ✅ | ✅ | Invoked as a CLI tool (`oh-my-posh init pwsh ... \| Invoke-Expression`), not `Import-Module`. |
| `Aliases.psm1` | ✅ | ✅ | Lazy-loaded from `$DOTFILES_ROOT` path. Works wherever the repo is reachable. |
| `Load-Env.ps1` | ✅ | ✅ | Utility script, dot-sourced via `Test-Path` guard. |

---

### Why Terminal-Icons Must Be Windows-Only

`Terminal-Icons` loads `Import-Clixml` internally to read cached user-theme data. When files under `C:\Users\…\Terminal-Icons\0.10.0\` are read over a UNC/WSL path:

- The XML parser in the WSL `pwsh` process cannot resolve Windows-absolute `InstalledLocation` paths
- `Import-Clixml` throws: *"Name attribute for dictionary key is incorrectly specified"*
- The null `$Matches[1]` that follows crashes any code using the returned object

The fix: import Terminal-Icons **before** dot-sourcing the repo profile, inside the Windows bootstrap profile, where all paths resolve correctly:

```powershell
if ($IsWindows -and $PSVersionTable.PSEdition -eq 'Core') {
    try {
        Import-Module Terminal-Icons -ErrorAction Stop
    } catch {
        # resilient: bad cache skipped silently
    }
}
```

---

### How to Avoid UNC Recursion and Nested Module Imports

The profile chain is one-directional:

```
Windows bootstrap → repo profile (via UNC)
```

**Never** have the repo profile import anything from a Windows-absolute path (`C:\…`). If it does, it will silently fail when loaded from a plain WSL `pwsh` session. Use `DOTFILES_ROOT`-relative paths exclusively.

**Never** have the Windows bootstrap dot-source itself or create a self-referencing loop. The bootstrap sets `DOTFILES_ROOT` once; if the repo profile also tries to resolve `DOTFILES_ROOT` and it's already set, it skips — that guard is intentional.

Use explicit one-shot guard variables for each layer:

- `DOTFILES_WINDOWS_BOOTSTRAP_LOADING` / `DOTFILES_WINDOWS_BOOTSTRAP_LOADED`
- `DOTFILES_PWSH_PROFILE_LOADING` / `DOTFILES_PWSH_PROFILE_LOADED`
- `DOTFILES_MODULAR_PWSH_LOADING`

**When adding a new module to the repo profile**, always wrap it:

```powershell
if (Test-Path $modulePath) {
    Import-Module $modulePath -ErrorAction SilentlyContinue
}
```

---

### How to Safely Add a New Module

1. **Determine host scope**: Windows-only, cross-platform, or WSL-only.
2. **Windows-only**: add the `Import-Module` call to the Windows bootstrap profile (`C:\…OneDrive\…\Microsoft.PowerShell_profile.ps1`), guarded by `$IsWindows -and $PSVersionTable.PSEdition -eq 'Core'`. Also add it to the loader template in setup-pwsh7.sh so `just setup-pwsh7` regenerates it correctly.
3. **Cross-platform**: add to config.ps1 with a `Get-Module -ListAvailable` guard.
4. **WSL-only**: add to linux.ps1, guarded by `if ($IsLinux)`.
5. Run `just setup-pwsh7` if you edited the Windows bootstrap template.

---

### VS Code Shell Integration Hardening

Manual shell integration is intentionally **guarded and idempotent**:

- Only runs when `TERM_PROGRAM=vscode`
- Loads once per process via `DOTFILES_VSCODE_SHELL_INTEGRATION_LOADED`
- Uses application-command lookup (`Get-Command ... -CommandType Application`) in PowerShell
- Skips UNC/WSL-network script paths to reduce cross-host contamination risk

Reference locations:

- `.shell_theme_common.ps1` for PowerShell integration guard
- `.shell_init.sh` and `shell/zsh/config.sh` for zsh integration guard

---

### Sandboxed Verification Pattern

Use this verification profile for Windows-side startup hardening tests:

1. Start `pwsh.exe` with `-NoProfile -NonInteractive`
2. Clear process env except `PATH`
3. Dot-source `C:\Users\<user>\OneDrive\MyDocuments\PowerShell\Microsoft.PowerShell_profile.ps1`
4. Capture warnings/errors, module trace, forbidden path hits, depth/cycle checks

Expected healthy outcomes:

- No runtime startup errors in smoke test (`$Error.Count = 0`)
- No forbidden module loads from `\\wsl.localhost\`, `\\wsl$\`, or `/home/.../PowerShell/Modules`
- No nested module chain depth > 3
- No circular chain in `bootstrap -> repo profile -> integration -> loader`

---

### Troubleshooting Residual Trace Warnings

`Trace-Command` can report warnings that do **not** indicate a broken startup path. Treat traces and runtime checks separately.

Benign/expected in constrained non-interactive tests:

- PSReadLine prediction warnings when output is redirected or VT is unavailable
- Verbose command-discovery/import messages that do not produce `ErrorRecord` entries

Treat as actionable only when one or more of these are true:

- Runtime smoke check shows `$Error.Count -gt 0` after dot-sourcing profile
- Bootstrap catch path triggers (`❌ Error loading dotfiles PowerShell profile` in normal startup)
- Forbidden path/module detections are non-empty
- Circular chain detector returns one or more cycles

Recommended triage order:

1. Run smoke check first (`pwsh -NoProfile` + dot-source profile + inspect `$Error.Count`)
2. If non-zero, inspect top `ErrorRecord.ScriptStackTrace`
3. Run trace diagnostics only after runtime errors are resolved
4. Re-run full sandbox report to confirm regression-free startup

## 4. Provisioning

### What the Windows Bootstrap Installs

Run bootstrap.ps1 on a fresh Windows machine:

| Task | Tool |
|------|------|
| Symlink or copy `powershell.config.json` | `New-Item -ItemType SymbolicLink` |
| Install `oh-my-posh` | `winget install JanDeDobbeleer.OhMyPosh` |
| Install `Terminal-Icons` to `CurrentUser` scope | `Install-Module -Name Terminal-Icons` |
| Install `PSReadLine` to `CurrentUser` scope | `Install-Module -Name PSReadLine` |
| Configure Oh My Posh themes | setup-themes.ps1 |

> **Idempotency**: every step is wrapped in a `if not already present` check, so re-running is safe.

---

### What the WSL Bootstrap Installs

Run bootstrap.sh from inside WSL:

| Task | Tool |
|------|------|
| Symlink `.bashrc`, .zshrc, `.shell_common`, `.shell_functions` | `ln -sf` |
| Install `oh-my-posh` | secure-installer with checksum (secure-install.sh) |
| Install Zsh + Oh My Zsh (Linux/WSL only) | install_zsh.sh |
| Verify MCP environment (`mcp/.env`) | existence check only |
| Install VS Code extensions | vscode.sh |

After the shell bootstrap, run `just setup-pwsh7` from WSL to write the Windows bootstrap profile.

---

### Keeping Provisioning Idempotent

Every install step must follow the pattern:

**Bash:**
```bash
if ! command -v <tool> &>/dev/null; then
    # install
fi
```

**PowerShell:**
```powershell
if (-not (Get-Command <tool> -ErrorAction SilentlyContinue)) {
    # install
}
if (-not (Get-Module <Module> -ListAvailable)) {
    Install-Module -Name <Module> -Force -Scope CurrentUser
}
```

Do not use `Install-Module` without `-Scope CurrentUser` — system-scope writes require elevation and will fail silently in CI.

The state-management.sh library (sourced in bootstrap.sh) provides `record_state` / `check_state` helpers to mark steps as complete and skip them on re-runs.

---

### How to Add a New Provisioning Step

1. **Bash bootstrap** (bootstrap.sh): add a new guarded `if` block. Source state-management.sh to mark it complete.
2. **PowerShell bootstrap** (bootstrap.ps1): add a new guarded `if (-not ...)` block before the final success message.
3. **Windows loader template**: if the step affects the Windows `pwsh` session, edit the `LOADER_CONTENT` heredoc in setup-pwsh7.sh. Run `just setup-pwsh7` to regenerate.
4. **Justfile task**: if the step should be independently runnable, add a `just` recipe in justfile.

## 5. Modifying the System

### Adding New Aliases or Functions

| If the alias/function is… | Add it here |
|--------------------------|-------------|
| Simple navigation, cross-platform | aliases.ps1 (PowerShell) and aliases.sh (Bash/Zsh) |
| A standalone utility function, cross-platform | functions.ps1 |
| Complex (calls multiple cmdlets, has parameters) | Aliases.psm1 + proxy at bottom of Microsoft.PowerShell_profile.ps1 |
| Windows-specific | windows.ps1 |
| Linux/WSL-specific | linux.ps1 |

After adding to `Aliases.psm1`, run `updatealiases` in a live `pwsh` session to regenerate the proxy stubs automatically.

---

### Adding New Platform-Specific Behaviour

1. Identify detection: `$IsWindows`, `$IsLinux`, `$IsMacOS`, or `$env:WSL_DISTRO_NAME` for WSL specifically.
2. If it is PowerShell behaviour, add to `shell/platform-specific/<platform>.ps1`.
3. If it is a shell function (bash/zsh), add to `shell/platform-specific/<platform>.sh` (sourced by loader.sh).
4. If it spans both, add to both files and use the correct guard in each.

Example — WSL-only tweak in PowerShell:
```powershell
# in shell/platform-specific/linux.ps1
if ($env:WSL_DISTRO_NAME) {
    # WSL-specific block
}
```

---

### Adding New `tools.d` Scripts

environment.ps1 automatically dot-sources every `*.ps1` file it finds in ps1, sorted by filename. This is the correct place for standalone tool-specific PATH or environment setup (e.g., `rust.ps1`, `nvm.ps1`).

- Drop a `<toolname>.ps1` into ps1.
- Prefix the filename with a number (`10-rust.ps1`) to control load order.
- Always guard with `Test-Path` or `Get-Command` so missing tools produce no noise.

The bash equivalent is sh; each `.sh` file is sourced by loader.sh in the same sorted manner.

---

### Adding New PowerShell Modules Without Breaking Host Separation

Follow this checklist:

- [ ] Identify whether the module requires Windows-specific DLLs or Windows-only paths
- [ ] If yes → Windows bootstrap only (see Section 3 — How to Safely Add a New Module)
- [ ] If no → config.ps1 with `-ListAvailable` guard
- [ ] Never import using a C:-absolute `ModuleBase` path from the repo profile
- [ ] Never import a module that calls `Import-Clixml` against Windows-installed cache paths from a WSL process
- [ ] If adding to the bootstrap template, edit setup-pwsh7.sh and regenerate with `just setup-pwsh7`
- [ ] Verify the live Windows profile with: `pwsh.exe -NoLogo -NoProfile -Command '. $PROFILE.CurrentUserCurrentHost; "OK"'`

### Host-Aware Branching Logic

```
At any decision point in PowerShell code:

$IsWindows  ──────►  Windows-native paths (C:\…), winget, Terminal-Icons,
                     Windows registry, Start-Process, Explorer integration

$IsLinux and
NOT $env:WSL_DISTRO_NAME  ──►  Pure Linux server paths, apt/yum, no GUI

$IsLinux and
$env:WSL_DISTRO_NAME  ──────►  WSL paths (/home/…, /mnt/c/…),
                                interop with Windows executables (.exe),
                                UNC path awareness

$IsMacOS  ──────────────────►  Homebrew, macOS keychain, open command

Unknown  ────────────────────►  Skip gracefully, warn with Write-Warning
```

---

### Key Invariants

| Invariant | Enforced by |
|-----------|------------|
| Terminal-Icons only loads on Windows | `$IsWindows -and PSEdition -eq 'Core'` guard in bootstrap |
| Repo profile is WSL-path-safe | All paths built from `$env:DOTFILES_ROOT`, no hardcoded C: |
| Bootstrap is regenerable | `just setup-pwsh7` rewrites Windows profile from template |
| Aliases.psm1 never imported at startup | Proxy functions deferred to first call |
| OneDrive excluded from PSModulePath | Filter applied before any module import |
| No profile loop | Bootstrap sets `DOTFILES_ROOT`; repo profile skips re-setting if already defined |
